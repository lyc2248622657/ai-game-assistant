# AI 辅助开发方法论（实战案例沉淀）

> 目的：把 ai-game-assistant 开发中"用 AI 解决真实问题"的方法沉淀为可讲述的实战案例，
> 对应岗位要求：**AI 智能体工程师（数据敏感 + 评测意识 + Claude Code/Codex 实际交付 + 开源作品）**、
> **FDE 前置部署模式（拆需求 → Agent 编排/MCP/RAG → 方法论）**。
> 本文所有结论均来自本项目真实开发记录，非演示性内容。

---

## 一、提示词工程：模板化 + 预算控制

**问题**：Agent 身份、游戏规则、工具说明混在一个大 prompt 里，改一个游戏要改全部；长会话 token 爆炸。

**做法**（`backend/app/agents/prompts.py`）：
1. **模板化**：角色（system）/ 规则（游戏规则与工具约束）/ 任务（当前意图）三分离，可复用可演进；
2. **注册表驱动**：游戏身份/实体类型/识别线索/数据源全部声明在 `config/games.yaml`，
   prompt 与图节点从注册表**动态派生**——新增第三个游戏只需登记 yaml + 建数据目录，不改任何 Agent 代码；
3. **上下文预算**：`prepare_history` = 会话摘要 + 最近 8 条，历史超窗自动压缩，
   实测控制每次调用 token 成本（对话级 usage 事件可观测：`⚡ 本轮消耗 N token（M 次调用）`）；
4. **JSON 解析失败重试一次**：意图识别输出 JSON，解析失败自动重试，稳定率实测 100%。

**教训**：prompt 里的"游戏专属术语"（明日方舟分支/职业）会被原神式 Validator 误判非法——
官方源数据天然可信时不做幻觉硬校验，只检查引用缺失（记录不阻断）。

## 二、Agent 编排：状态图 + 质检 + 失败兜底

**问题**：单轮 LLM 问答不可靠：意图误判、编造细节、工具偶发失败中断整轮。

**做法**（`backend/app/agents/graph.py`，LangGraph 8 节点状态图）：
1. **supervisor 主管 → 子代理委派**：主管识别游戏 + 域判别（entity/knowledge/event）+ 委派单，
   genshin/arknights/knowledge 子代理独立执行（SSE 推送 subagent 事件，前端可视化委派链路）；
2. **Plan-Execute-Refine**：plan 拆结构化子任务 → tool 循环执行（Function Calling ≤3 轮）→
   replan 规则预检（建议工具未调用/工具返回未收录 → 补充计划二次执行，上限 1 轮防死循环）；
3. **reflect 质检节点**：synthesize 后自检（忠实性/覆盖度/幻觉），不合格回炉一次——
   **消融实验证明去掉 reflect 幻觉 0.75→2.0 条/评测**，是防幻觉最大贡献组件；
4. **工具失败自动重试**：瞬时失败（网络/上游抖动）自动重试一次再标 error，避免 5xx 中断整轮。

**量化证据**（组件消融，5 配置 × 4 条）：
| 配置 | acc | 幻觉/条 | 结论 |
|---|---|---|---|
| 全链路 | 0.950 | 0.75 | 基线 |
| 去 replan | 0.912 | 1.0 | 正贡献中等 |
| 去 reflect | 0.887 | **2.0** | 防幻觉关键 |
| 去混合检索 | 0.725 | 1.5 | 准确率 -0.225 |
| 去记忆注入 | 0.688 | 0.75 | 准确率 **-0.262** |

**教训**：每个组件都要有可观测的贡献证据，不做"看起来有用"的过度工程。

## 三、评测闭环：定义指标 → 搭评测 → 归因修复（岗位最看重）

**问题**：回答"感觉"准不准，无法量化，无法回归。

**做法**（`backend/scripts/eval/`）：
1. **评测集**：原神 30 + 明日方舟 20 = 50 条，四类题型（entity 实体 / knowledge 知识 / edge 边界 / complex 复合）；
2. **指标**：LLM-as-Judge 四指标（准确率 / 忠实性=引用支撑 / 覆盖度=期望要点 / 幻觉条数）+ **RAG 命中率**
   （期望要点是否被引用资料覆盖，直接反映检索召回质量）；
3. **Judge 校准**：人工校准集逐条对照打分 → MAE/一致率/偏差模式 → **暴露并修复真问题**
   （Judge 看不到引用正文导致误判编造 → 修复后 Judge 与人工标注完全一致 MAE=0）；
4. **增量回归**：`--only-failed` 只重跑失败/低分/含幻觉用例（省 token：全量 30 条 ≈ 11.6 万 token/轮）；
5. **归因闭环**：每次失败 → 定位根因（prompt 误判 / 数据错误 / 检索不到 / 兜底编造）→ 修数据或逻辑 → 全量重跑验证。

**实绩**（2026-10-11 全量）：entity 0.9 / knowledge 0.86 / edge 1.0 / complex 1.0，**幻觉清零**，失败列表为空。
已修复的真实问题：胡桃生日数据错误（7月15日→12月20日）、配队兜底编造来源、"万达国际"无库内条目、
列举类 top_k 截断（4→12）。

## 四、RAG 检索：多路召回 + 可观测命中率

**问题**：单路向量检索漏召回（问圣遗物/武器/循环时拿不到关联数据）。

**做法**（`backend/app/rag/retriever.py`）：
1. **四路召回**：名称命中置顶（四档） + 向量（Chroma/bge-small-zh 512 维） + **BM25 稀疏检索**
   （无外部依赖的 Okapi BM25，中文 bigram + 英文分词，按数据指纹缓存索引） + 关键词兜底；
2. **元素×职能精确补充**：如"火系主C"→ 胡桃/迪卢克/香菱精确召回；
3. **角色关联联动**：`related_gear` 把配队/武器/圣遗物按 recommended/tags/文本命中角色名一起给（胡桃 → 魔女套/护摩/蒸发队）；
4. **列举类放大 top_k**："有哪些五星"类问题 top_k 4→12；
5. **评测可观测**：RAG 命中率指标让"检索质量"可量化、可回归。

## 五、数据管道：官方源优先 + LLM 补缺 + 交叉验证（防幻觉）

**问题**：LLM 直接生成游戏数据会编造；纯手工录入不可持续。

**做法**（`backend/app/tools/game_entity.py`）：
1. **官方 wiki 优先**：BWIKI/PRTS 抓取 → 字段补全（只补缺失不覆盖已有）→ 写回动态缓存；
2. **LLM 仅补推断字段**：官方源失败时原神走「LLM 生成 + wiki 交叉验证」兜底；
   **明日方舟不 LLM 兜底**（防编造游戏归属/星座等原神式幻觉），如实返回"未收录"；
3. **引用校验白名单**：回答引用的实体必须存在于库内 id/name 白名单；
4. **增量补全链路**：静态库 → 动态缓存 → wiki → LLM → 交叉验证 → 增量写回，回答可溯源。

## 六、工程实践：测试 / CI / 部署 / 成本可观测

- **测试**：68 passed（解析器 / 图编译 / 工具 / 事件引擎 / BM25 / 评测集格式 / 智能命名 / 最近实体 / 信息补全）；
