# 设计决策记录（Design Decisions）

> 记录 ai-game-assistant 关键架构决策的**动机与取舍**：为什么选这个方案、替代方案是什么、
> trade-off 在哪、事后验证结果如何。所有结论均来自本项目真实实现与评测数据（见 `backend/` 代码与
> `data/eval_report_v5.json`），不包含未经验证的推测。

---

## 1. 为什么用 LangGraph，而不是 CrewAI / AutoGen / 手写 while 循环

**背景**：项目需要四条明确的控制流能力——supervisor 委派、条件路由、动态重规划（≤1 轮）、
Reflection 自检回炉，并且要为消融实验提供"逐组件开关"能力。

**决策**：LangGraph 显式状态图。

| 方案 | 优势 | 本项目中的代价 |
|---|---|---|
| LangGraph 状态图 | 节点/边/条件路由**显式可编程**；每个节点可单独注入/移除（消融实验直接靠 `state["ablate"]` 开关实现）；replan/reflect 作为显式节点进入图，可观测（SSE 事件流） | 样板代码较多；图结构的学习成本 |
| CrewAI | 角色/任务高层抽象，几行搭起多 Agent 协作 | 控制流隐式（任务委派由框架决定），无法精确实现 replan≤1/工具循环≤3 这类硬约束；逐组件消融困难 |
| AutoGen | 对话式多 Agent 消息编排 | 偏"Agent 之间用自然语言协商"，本项目 supervisor 只在少数场景委派子代理（刻意克制），不需要协商式编排 |
| 手写 while 循环 | 零依赖 | 状态管理、条件路由、事件发射、消融开关全要自己实现，可维护性差 |

**验证**：图内 6 节点全部进入 `tests/test_graph.py` 编译测试；replan/reflect/memory/hybrid 四组件
均有消融开关（`state["ablate"]`），支持 `scripts/eval/ablation.py` 逐组件关闭跑评测。

## 2. 为什么工具循环 ≤3 轮、重规划 ≤1 轮

**背景**：Function Calling 循环是 token 与延迟的主要来源；无上限循环会放大"模型反复调错工具"的失败模式。

**决策**：
- 工具循环：`tool_node` 内 `for _ in range(3)`，无工具调用即结束；第三次仍出工具调用则强制收尾。
- 重规划：`replan_node` 中 `replan_count >= 1` 直接跳过——最多补做 1 轮。

**动机**：游戏问答的多数问题在 1 轮工具调用内可解（实体查询/配队/材料换算均为单工具），
3 轮覆盖"先检索 → 再按结果追问 → 兜底"的典型链路；重规划是"计划执行后发现子任务未完成"的
异常路径，1 轮足够，超过说明计划阶段本身失败（应回到 supervisor 而非在工具层死循环）。

**代价**：极端复合问题（需要 3 轮以上工具+重规划）会被截断——评测集里 complex 类准确率 0.822
（judge 50 条，n=9）低于 entity 0.978，部分原因即在此；这是"成本可控"与"覆盖极长链路"之间的
显式取舍。

## 3. 为什么混合检索是"名称置顶 + 向量 + BM25 + 规则补充 + 关键词兜底"，而不是 RRF

> **修订（2026-10，第二轮修复）**：本节结论已被实现推翻——融合改为 **RRF**，见文末「修订说明」。
> 下面的原始论证保留，用于追溯当时的取舍理由。

**背景**：外部评价追问"为什么不用 RRF（Reciprocal Rank Fusion）"。

**决策**：不使用 RRF，采用**规则分层的加权融合**，理由：

1. **分数不可比**：BM25 分数已归一化到 [0.55, 0.95]，向量检索分数量纲不同、且会随集合变化——
   RRF 的前提是"各路给出可靠排序"，但本项目希望"名称精确命中"这种**强信号绝对置顶**
   （`_name_match_score`：精确=4 > 前缀=3 > 包含=2 > 子串=1），RRF 的 rank 融合会稀释这一强信号。
2. **规则路径不是 rank 结果**：第 ③ 路"元素×职能精确补充"（如"雷系副C"→ `element=雷 且 role 含副C`）
   是结构化精确查询，输出天然是"该答的答案"（score=0.95 置顶于普通向量结果之前），
   不是候选排序，无法进入 RRF 框架。
3. **融合代价小**：实测融合去重逻辑简单（`merged` 按 doc_id 取高分），main 链路无需额外调参。

**各路的失败模式分工**：
| 路 | 解决的失败模式 | 事后验证 |
|---|---|---|
| 名称置顶（≤3） | "胡桃用什么圣遗物"中实体名必须强相关 | 名称命中质量函数 2.2 修复（query 含多实体名时区分主次） |
| 向量召回（top5） | 语义相似但无共享词的查询（"适合什么角色"） | 消融 no_hybrid 见 `data/ablation_report.json` |
| BM25（top5） | 中文命名实体/缩写精确匹配（干员名、武器名） | `tests/test_bm25.py` 中英混合分词 |
| 元素×职能（≤2） | "雷系副C有哪些"这类跨字段组合查询 | 评测 knowledge 类修复记录（见 §6） |
| 关键词/全文兜底 | 向量库不可用、零命中 | 兜底路径含 team 优先，防配队问题空答 |

**已知代价**：向量分数量纲未归一化到与 BM25 同尺度，融合时存在潜在偏差；后续若向量分数漂移
明显，可切 RRF 或统一归一化（当前 220 条评测 RAG 命中 0.947，暂未触发）。

**修订说明（2026-10，第二轮修复）**：上述"潜在偏差"实际是**结构性缺陷**，已改为 RRF：

1. 原实现把 BM25 分缩放到 **[0.55, 0.95]** 后与余弦相似度（典型 0.35~0.7）取 `max`，
   导致**词法命中必然压制语义命中**——一个只命中单个二元组的垃圾结果也能赢过真正相关的向量命中；
2. 且 BM25 候选（≥0.55）天然全部通过 0.5 阈值，而余弦 <0.5 的相关结果全被丢弃；
3. 本节的反对理由"RRF 会稀释名称强信号"**不成立**：名称命中在实现中仍**独立置顶**（不参与 RRF），
   规则补充路（元素×职能）也仍在融合之后追加，两者都未进入 rank 融合。

现实现见 `app/rag/retriever.py::_rrf_fuse`（k=60，按名次融合；展示用 score 保留各路原分量级）。
待办：`retrieval_score_threshold` 等三个阈值仍需按评测集重新标定。

## 4. 为什么保留自研 ReAct 循环（scratch_react），而不是只用一个框架

**背景**：LangGraph 全链路质量更稳，但每请求多节点多次 LLM 调用，成本和延迟高。

**决策**：两条链路共存（`scripts/compare_react.py` 同一组 6 题对比），共享 `hybrid_retrieve` 检索层。

**验证结果**（2026-10，`data/compare_react.json`）：
- ReAct 在核心事实正确性上持平（6 条对比集内复核无幻觉），省约 **35% 耗时**、**~1.6k token/条**；
- 代价：检索策略简化（无 Reflection 质检）、无引用标注——已通过共享 hybrid_retrieve 与
  ReAct 侧 citations 输出收敛差距（judge_compare 忠实性自动核验）；
- 结论：默认走 LangGraph（质量优先）；ReAct 作为"低成本快速通道"保留，且验证了
  "知道框架边界在哪"——不是所有场景都需要完整图。

## 5. 记忆分层的实现与保真取舍

**背景**：外部评价追问"摘要滚动压缩的触发条件是什么？压缩后怎么保证关键信息不丢失？"

**实现**（三层，MemGPT 式分层的落地子集）：
| 层 | 内容 | 注入方式 |
|---|---|---|
| core | 用户偏好（`user_memory.py`） | 全量注入，不入向量库 |
| working | 当前会话摘要（`session_memory.py`） | 摘要 + 最近 N 条消息（`prepare_history`） |
| external | 历史会话事实（摘要/偏好/常问实体） | Chroma「user_memory」向量召回，`MEMORY_TOP_K=5`，按 `game_id` 隔离 |

**滚动压缩触发与保真**（`session_memory.py`）：
- **触发条件**：`SUMMARY_THRESHOLD = 12`——会话消息数 ≥12 才生成/更新摘要；
- **增量压缩**：`summary_from` 游标记录已压缩位置，只压缩"游标之后、最近 2 条之前"的消息
  （`pending = [m for m in msgs if m["id"] > cursor][:-2]`）——旧摘要 + 新消息重新压缩，
  transcript 长度有界，不随轮次线性增长；
- **保真机制**：① 旧摘要整体保留并作为新摘要的输入（早期信息不丢）；② 最近 2 条消息永不压缩
  （进行中上下文完整）；③ 摘要由 LLM 生成、写入异步触发，失败静默降级（不阻塞对话）；
- **已知边界**：压缩依赖 LLM 摘要质量，极端长会话下极端次要细节可能被摘要丢弃——这是
  "token 成本有界"与"无损全量记忆"的取舍；Memory RAG 向量层（external）承担跨会话事实恢复。

## 6. 失败修复记录（踩坑 → 根因 → 修复 → 验证）

评测闭环（`scripts/eval/`）每次失败都走"定位根因 → 修数据或逻辑 → 全量重跑验证"，
以下是已修复的真实问题：

| 问题 | 根因 | 修复 | 验证 |
|---|---|---|---|
| 胡桃生日答 7月15日 | 知识库数据错误 | 7月15日 → 12月20日，补 wiki 验证映射 | 评测集内生日题全部命中 |
| "万达国际"配队查询答非所问 | 库内无该配队条目，模型编造兜底 | `teams.json` 入库"万达国际" | knowledge 类配队题通过 |
| 列举类"有哪些角色"漏答 | `top_k=4` 截断丢角色 | 列举类识别（有哪些/列出/所有…）→ `top_k=12` | entity 列举题不再漏项 |
| 出现"XX·主C 通用队"伪配队 | 兜底模板编造来源 | 删除伪配队兜底模板 | 消融/评测无编造来源用例 |
| plan 意图误判 / synthesize 编造细节 / validator 定位枚举过严 | 各节点 prompt/逻辑缺陷 | 分别修正 prompt 与枚举逻辑 | 失败用例归零（集内） |

**方法论沉淀**：评测集 220 条（numeric 170 规则判定 + judge 50 交叉评审，带 95% 置信区间）
是这套修复闭环的"回归防线"——`--only-failed` 增量回归只重跑失败/低分/含幻觉用例，省 token。

## 7. 当前已知短板与后续取舍（不放大结论）

- **knowledge 类评测准确率 0.671（judge 50，n=14）**：元素反应/圣遗物套件等知识题检索覆盖不足，
  优先补知识库条目与检索路，而非加模型轮数；
- **消融 20 条 numeric 子集上各组件无显著正贡献**（`data/ablation_report.json`）：组件收益需在更大
  judge 集上验证，现有结论不放大；
- **Chroma 查询延迟（历史 P95≈11.9s 首发加载）**：已按需服务端模式/预热策略缓解，多用户并发仍需
  向量库服务化；
- **Windows 优先**：脚本以 PowerShell 为主、桌面 key 读取流程为 Windows 习惯——跨平台不是当前目标，
  是"单用户本地工具"定位的显式取舍。

---

## 8. 结论：这套取舍的适用边界

上述决策服务于一个**单用户、本地优先、两个固定游戏域**的智能问答工具：
- ~~强信号优先的检索融合（而非 RRF）~~ → **已改为"名称置顶 + RRF"**（见 §3 修订说明），
  在"固定小知识库 + 名称强标识"场景仍然成立（强信号不走 rank 融合）；
- 三层记忆与增量压缩在"长会话个人助手"场景成立；
- 若切换到"多用户 SaaS / 开放域问答 / 高并发"，检索融合、记忆层、部署形态都需要重新权衡——
  本文件即为这些"为什么"留档，避免架构决策失去可追溯性。
