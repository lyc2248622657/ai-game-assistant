## 1. P0：确定性缺陷（能指出触发路径，建议优先修）

### P0-1 LangGraph 状态通道缺失：三个字段被框架静默丢弃

**证据**

- `backend/app/agents/state.py:37-86` 的 `AgentState` 只声明了 29 个字段，**不含** `memory_context` / `guides` / `related_entities`。
- `backend/app/agents/graph.py` 却在节点里写它们：
  - `memory_context`：写 `graph.py:88,91`（supervisor 节点）→ 读 `graph.py:317`（tool 节点）、`graph.py:622`（synthesize 节点）
  - `guides`：写 `graph.py:609` → 读 `graph.py:665,666`
  - `related_entities`：写 `graph.py:636` → 读 `graph.py:663,664`
- LangGraph 的实际行为（`langgraph/pregel/_algo.py:308-313`）：
  ```python
  elif chan in channels:
      pending_writes_by_channel[chan].append(val)
  else:
      logger.warning(f"Task {task.name} ... wrote to unknown channel {chan}, ignoring it.")
  ```
  **写入未声明通道 = 直接忽略，只打一条 warning。**

**后果（三处都是真实功能失效，不是理论问题）**

1. **记忆注入是死代码**：supervisor 里 `_load_memory_context()` 花钱算出来的 `memory_context`，到 tool/synthesize（下一个超步）必然读不到 → 永远是 `None`。每轮请求都在为此付一次 Chroma 查询 + embedding 计算，收益为 0。
2. `ChatResponse.guides` **永远是 null**（`api/chat.py:166`）：synthesize 写的 `guides` 到不了最终状态。SSE 能显示攻略卡片，是因为 `_emit` 走了已声明的 `events` 通道，属于"歪打正着"。
3. `ChatResponse.related_entities` 同样永远为 `[]`（`api/chat.py:165`）。

**验证方式**：AST 比对 `state.py` 声明 vs `graph.py` 引用，输出即为上述 3 个键；行为依据是已安装 langgraph 1.2.14 的源码。
另外可直接在服务日志里 `grep "wrote to unknown channel"` 复现。

**最小修复**：在 `AgentState` 中声明这三个字段。
```python
memory_context: Optional[str]
related_entities: Optional[list[str]]
guides: Optional[dict]
```

### P0-5 前端 Markdown：所有链接都指向第一个 URL

`frontend/src/utils/markdown.tsx:71`
```ts
const idx = Number(seg.slice(5, -1))
```
占位符是 `\u0000URL{n}\u0000`（长度 6），数字在下标 **4**，而 `slice(5,-1)` 取的是第 6 个字符到倒数第一个之间——**永远是空串**。

已用 node 实测确认：
```
'\u0000URL1\u0000'.slice(5,-1) === ''   -> Number('') = 0
'\u0000URL1\u0000'.slice(4,-1) === '1'
```
**后果**：一条回答里出现 ≥2 个 URL 时，每个链接的 `href` 和显示文本都变成 `protectedParts[0]`（第一个链接）。回答里同时给「B站视频 + wiki 攻略页」时，用户点哪个都跳错。

**修复**：`seg.slice(4, -1)`。

### P0-6 SQLite 连接从不关闭 + 没有 WAL

**连接泄漏**：`with sqlite3.connect(...) as conn:` 只管理**事务**，不关闭连接。`backend/app/memory/` 下 12 处都是这个写法（`store.py:31,55,68,76,94,100,127,138,160,168`；`session_memory.py:34,47,54,100`；`user_memory.py:37,51,88`），且**全文件没有任何 `.close()`**。

**后果**：正常路径靠引用计数回收；但异常路径上 traceback 持有栈帧 → 连接（及 fd）与异常对象同寿命，而 FastAPI 会把异常链保留在 500 响应里。长时间跑 + 频繁报错就会积累 fd。
每次查询都新建连接，`get_session()` 一次要开 2 个连接（`store.py:75-82` 里还调了 `count_messages`），`list_sessions()` 是 N+1（`store.py:116`）。

**并发**：全仓库没有 `PRAGMA journal_mode=WAL`、没有 `busy_timeout`。默认 rollback journal 下写锁会挡住读，而 `api/chat.py:221-233` 会连续写 2 条消息 + 标题 + 记忆，全在线程池里并发执行 → 高并发下会 `database is locked`。

**修复**：`contextlib.closing` 或统一封装 `_conn()`；初始化时设 `journal_mode=WAL`、`busy_timeout=5000`；`list_sessions` 改成一次 `GROUP BY` 统计。

## 2. P1：架构与契约问题

### 2.1 依赖与可复现性：三个互不一致的目标环境

- `backend/requirements.txt` 全是下限（`langchain>=0.3`、`langgraph>=0.2`、`chromadb>=0.5`…），**无 lock 文件、无 `pyproject.toml`**。代码是按 langgraph 0.2 时代的 API 写的，实际装的是 1.2.14——这次能跑通是运气，不是保证。
- 已装包版本与代码假设的偏差值得单独回归：`langchain 1.x` 的 `message.content` 可以是 block 列表，而 `graph.py:629`、`chat.py:82` 都按 `str` 用（`resp.content or ""` 再 `.strip()`）。

### 2.2 节点返回整个 state（这掩盖了 P0-1）

`graph.py` 每个节点都是 `def xxx_node(state: AgentState) -> AgentState`，**原地 mutate 后把整个 state 返回**。这违反 LangGraph 的"节点返回增量"约定，直接带来两个后果：

- 只要忘了在 `AgentState` 里声明字段，就静默丢失（P0-1 就是这么漏的）；
- `state.py:16-34` 的 `_dedup_extend` reducer 里有这么一段：
  ```python
  if len(new) >= len(cur) and all(_elem_key(x) in cur_keys for x in new):
      return list(new)
  ```
  它的唯一作用就是让"返回全量"表现得像覆盖。这是把框架的增量语义偷偷改成全量语义的补丁，一旦上 checkpointer / 中断恢复就会失真。

**建议**：节点只返回自己改动的键（`return {"citations": citations}`），删掉 `_dedup_extend` 里那段启发式。

### 2.4 阻塞调用侵入异步/请求关键路径
