# 技术栈对比与优化建议

> 对照基准：2026 年主流 AI 应用 / Web 全栈实践
> 方法：读取仓库实际依赖（`requirements.lock` 148 包、`package.json`）＋ 逐层核对"用了什么"与"用到了什么程度"
> 一句话结论：**框架版本不算旧，问题在"用法停在框架能力的 10%"，以及缺一套可观测/评测的标准底座。**

---

## 一、结论先行

1. **LLM 框架是当代的，用法是初代的**。LangGraph 1.2 提供持久化、断点续跑、人工审核中断、事件级流式、子图、故障重试、可观测接入等能力，
   项目只用了最基础的 `StateGraph` 编排 + `stream_mode="values"`（节点级事件），**其余全部未用**。
2. **RAG 只做到"能召回"，没做到"可评估地召回"**：没有 rerank、没有查询改写、没有检索评测基线；评测是自己写的跑分脚本，未接主流评测/追踪体系。
3. **工程基础设施缺的是"标准化"，不是"功能"**：有 CI、有 Docker、有测试，但没有结构化日志、链路追踪、指标、依赖扫描、类型检查、迁移管理——
   这些恰恰是"能不能被团队接手"的分水岭。
4. **前端落后一个代际**（React 18 / Vite 5 / Tailwind 3），但**这不是当前瓶颈**；瓶颈在后端可观测性与 RAG 质量。
5. **一半的"主流升级"不该做**：单机定位下，SQLite、Chroma 嵌入模式、PyInstaller、单进程 uvicorn 都是合理取舍，换成 Postgres/Milvus/K8s 是负收益。

## 三、逐层差距与建议

### 3.1 Agent 层：框架能力只用了约 10%（**最该补的一块**）

LangGraph 官方能力清单里，项目**完全没用**的有：

| 能力 | 能解决什么 | 现状 |
|---|---|---|
| Checkpointer（持久化） | 崩溃/重启后续跑、对话级状态回放 | 每轮 `invoke(state)` 从零开始，无持久化 |
| Interrupt / 人工审核 | 危险工具（写计划、删向量）执行前挂起等人确认 | 无（`build_plan` 的写操作直接落库） |
| Event streaming | token 级流式、逐事件（`astream_events`） | 只有节点级 `agent_start/end`，回答是**整段**推送 |
| Subgraph | 子代理独立成图、可单独测试 | 8 个节点平铺在一个图里 |
| Fault tolerance（retry/timeout policy） | 节点级重试与超时 | 无（只有工具层手写一次重试） |
| Time travel | 用历史 checkpoint 重放调试 | 无 |
| LangSmith / OTel 可观测 | 每条链路可回放 | 无 |

**建议（按 ROI）**
1. **显式接 `astream_events` 做 token 流式**：现在 `answer` 事件推的是整段最终文本（`chat.py` 里 `delta: fa`），
   前端"逐字出现"的体验其实是假的。这是**用户能直接感知**的差距，改动集中在一个流式函数。
2. **加 `SqliteSaver` checkpointer**（`langgraph-checkpoint-sqlite`）：把会话状态落 SQLite，
   好处是①崩溃可恢复 ②支持 `interrupt` ③调试时能 `get_state_history`。单机场景成本极低。
3. **给写操作加 `interrupt`**：`save_build_plan`、`delete` 类工具执行前挂起，前端弹确认——这是"Agent 安全"的主流做法，
   也能在面试里讲清楚"为什么要人在环"。
4. 子图/时travel 不急着上，等 Agent 数量真变多再说。

### 3.2 RAG 层：缺"可评估的质量闭环"

| 差距 | 主流做法 | 影响 |
|---|---|---|
| 无 rerank | bge-reranker / Cohere Rerank / ColBERT，召回 20 → 重排 5 | 中文长文档下 top-5 精度明显偏低；你现在靠"名称置顶"补，属于用规则补模型的活 |
| 无查询改写 | Multi-Query / HyDE / step-back | 口语化提问（"这个角色强吗"）召回差 |
| chunk 策略硬编码 | 结构感知切分（标题层级）、父子块（small-to-big） | `document_qa` 按 600 字切，段落语义会被截断 |
| 无检索评测 | 建 golden set（query → 期望 doc id），跑 recall@k / MRR | **现在无法证明检索改动是变好还是变坏**；RRF 改动只能靠人工看 |
| 无向量库运维指标 | 集合版本、索引重建、ANN 参数 | 升级 embedding 模型时只能整库重建，无灰度 |

**建议**：先做**检索 golden set（50 条 query→doc_id）+ recall@5 脚本**（半天），
它能把"rerank 加不加""RRF vs 加权""top_k 调多少"从拍脑袋变成可对比。
这比直接加 rerank 更重要——**没有度量就没有优化**。

### 3.3 后端工程：从"能跑"到"可维护"

| 差距 | 主流 | 建议 |
|---|---|---|
| 手写 SQL + 无迁移 | SQLAlchemy 2.0 + Alembic | 已有 3 张表，现在引入成本最低；再加表就晚了 |
| 同步 SQLite 调用 | `aiosqlite` 或 SQLAlchemy async | 现在靠 `to_thread` 兜，能接受；表变多后再改 |
| `BackgroundTasks` 当队列 | ARQ / RQ / Celery（或单机就 `asyncio.Queue`） | 记忆维护、标题生成重启即丢——单机可接受，**别对外宣称"异步任务"** |
| 无缓存 | Redis / `cachetools`（单机） | 事件抓取、检索结果可加 TTL 缓存；单机用 `cachetools` 足够 |
| 无请求限流 | slowapi / 自研中间件 | 已有"鉴权失败限流"，可扩展为全局限流 |
| 无结构化日志 | structlog + request-id | **最便宜的高价值改造**：一次日志能定位到具体请求/会话/节点 |
| 无类型检查 | mypy（strict 子集）/ pyright | 5,900 行 app 代码，现在上成本可控；`TypedDict` 状态树正是 mypy 的强项 |
| 依赖无审计 | Dependabot + `pip-audit` / Trivy | 公开仓库尤其需要 |

### 3.4 前端：落后一个代际，但不是瓶颈

| 差距 | 主流 | 是否值得升级 |
|---|---|---|
| React 18 → 19 | 19 稳定，`use`/Actions/编译器 | **值得**（低风险，主要是依赖兼容） |
| Vite 5 → 7 | 更快、更好的 HMR | 值得（配置几乎不变） |
| Tailwind 3 → 4 | CSS-first 配置、构建更快 | 可选（迁移有配置成本，收益是 DX） |
| 手写 fetch + 自制 reducer | TanStack Query（缓存/重试/失效/乐观更新） | **强烈建议**：现在为"切会话竞态/重复请求"打的补丁，TanStack Query 天生解决 |
| 无 E2E | Playwright | 值得：一条"发消息→流式→引用卡片"的 E2E，比 20 个单测更能防回归 |
| 手抄类型 | OpenAPI → `openapi-typescript` 生成 | **强烈建议**：这次审计发现的 `snippet`/`content` 字段错位，就是手抄 drift 的典型 |

### 3.5 工程与部署

- **Python 打包代际**：主流已是 `pyproject.toml` + **uv**（`requirements.lock` 是上一代做法）。迁移成本约 1 小时，收益是可复现安装 + 依赖组（dev/prod）分离。
- **Node 20 已过维护期**：`frontend/Dockerfile` 里的 `node:20-alpine` 应升到 22/24 LTS（安全补丁不再下发）。
- **Python 3.11**：Docker/CI 可用 3.12（与你本地验证环境一致），减少"本地能跑、CI 行为不同"。
- **无 secrets 管理**：Key 明文存 `app_data/settings.json`。单机可接受，但要写进 README 的风险说明（已做），或接系统凭据库。
- **无依赖安全扫描**：公开仓库建议开 Dependabot（自动 PR）+ Trivy（镜像扫描），成本近乎为零。

### 3.6 可观测性（当前**最大**的体系缺口）

现状：没有 request-id、没有 trace、没有指标、没有会话级成本。
而 LLM 应用排障的特点是"**一次回答经过 4~8 次模型调用 + 检索 + 工具**"，没有 trace 就只能靠翻日志猜。

**建议（按投入排序）**
1. **request-id + 结构化日志**（半天）：`structlog`，每条日志带 `request_id / session_id / node / latency_ms / tokens`。
2. **LangSmith 或 Langfuse 追踪**（半天）：LangChain 生态一行 `LANGCHAIN_TRACING_V2=true` 即可接入；自托管用 Langfuse。
   面试时"我能回放任何一次回答的完整链路"是很有说服力的表述。
3. **指标**（1 天）：`prometheus-fastapi-instrumentator` 暴露 `/metrics`：QPS、P95、LLM 调用次数、token 消耗、检索命中率。
4. **按会话的成本核算**：现在是进程级计数器（并发下会互相污染），改为 per-request callback。

## 四、"不要升级"清单（避免过度工程）

| 常见建议 | 为什么这个项目**不该**做 |
|---|---|
| SQLite → PostgreSQL | 单用户、数据量 <20MB、无并发写；换 PG 只增加部署复杂度。**表结构上去 ORM 即可，DB 不用换** |
| Chroma → Qdrant/Milvus/pgvector | 集合规模几百~几千条，嵌入式 Chroma 的召回延迟已是毫秒级；换服务化向量库是纯负担 |
| PyInstaller → Tauri/Electron | 目标是"双击即用"，440MB 换不来启动速度；真要减小，先砍打包进去的 `transformers` 等未用依赖 |
| 自研令牌 → OAuth2/Authlib | 单用户无账号体系，OAuth 是负资产；当前"回环免令牌 + 暴露即令牌"更贴合场景 |
| 加 Redis / Celery | 单进程单机，引入后多两个要运维的组件；`asyncio.Queue` + SQLite 足够 |
| 上 K8s / 服务网格 | 单机工具，Docker Compose 已是上限 |
| 换 LangGraph 为 CrewAI/AutoGen | 现有图已能表达编排，换框架等于重写；真正缺的是 3.1 里那几项"框架能力没用" |
| 前端上 Next.js | 无 SSR/SEO 需求，Vite SPA 更轻 |

**判断标准**：这个升级是否解决你**已经观测到**的问题？没观测到就先建观测（3.6），再决定。

## 五、建议路线（按投入产出）

### 第一档：一周内（都是"低成本、高信号"）
1. request-id + 结构化日志
2. Langfuse/LangSmith 追踪接入（一条环境变量）
3. token 级流式（`astream_events`）
4. OpenAPI → TS 类型生成，替换手抄 `types/index.ts`
5. Node 镜像升 22/24；Python 升 3.12

### 第二档：一个月内（补"质量闭环"）
6. 检索 golden set + recall@k 脚本（先度量）
7. 基于度量加 **rerank**（bge-reranker-base，本地 CPU 可跑）
8. TanStack Query 替换手写 fetch（顺带消掉竞态补丁）
9. `pyproject.toml` + uv 迁移
10. Dependabot + pip-audit + Trivy

### 第三档：长期（按需）
11. LangGraph checkpointer + `interrupt`（写操作人工确认）
12. SQLAlchemy + Alembic（表数量增长前）
13. Playwright E2E（1~2 条关键路径）
14. React 19 / Vite 7 / Tailwind 4 升级
15. per-request 成本核算 + Prometheus 指标

## 七、怎么证明优化有效（避免"升级了但没变好"）

1. **先建基线**：当前 165 tests / 覆盖率 60% / 单轮 prompt 约 3~17k tokens / 检索无 recall 指标。
2. **每次只改一层**，用同一批 golden query 对比：recall@5、P95 延迟、单轮 token。
3. **把结论写进 `docs/`**：你已经在做（DESIGN-DECISIONS），继续保持"决策 + 证据"的记录方式——
   这比技术栈本身更能体现工程判断力。
