## 二、架构解析

### 2.1 分层与依赖方向

```
HTTP 层   app/api/*（26 端点）  ── 只做参数→调用→组装响应
编排层    app/agents/graph.py（LangGraph 8 节点）
          app/agents/a2a.py（协调者→子代理，仅 MCP/脚本可达）
          app/agents/scratch_react.py（手写 ReAct，仅对比实验）
能力层    app/tools/*（11 个工具：实体/策略/计划/事件/视觉）
检索层    app/rag/*（embedding → vectorstore(Chroma) → retriever(名称+向量+BM25+规则) → document_qa）
记忆层    app/memory/*（SQLite 会话/偏好 + Chroma 记忆向量）
基础层    app/core/*（config / errors / logging / usage / key_manager / sqlite / paths）
```

依赖方向基本自上而下，无反向环（`tools↔registry` 用延迟导入规避循环，属可接受的折衷）。

### 2.2 一次提问的完整链路（含成本）

```
POST /api/chat/stream
  └─ _prepare：校验 Key → 会话 → 历史 20 条 → initial_state
     └─ [1] supervisor  LLM×1（JSON 失败再 +1）：判游戏/域/子任务，加载记忆上下文
        └─ [2] route    纯规则
           ├─ retrieve  向量(embedding)+BM25+名称置顶+规则补充 → top_k(4/12)
           └─ tool      LLM×1~3 + 工具执行（失败重试一次）
              └─ [3] replan   LLM×0~1：子任务未完成则补做
                 └─ [4] synthesize LLM×0~1：把资料拼成回答 + 生成 citations
                    └─ [5] reflect    LLM×1：质检，不合格回炉一次（再 +1 次 synthesize）
   └─ 落库 + 后台任务：auto_title（LLM×1）、user_memory 偏好提取（LLM×1）、
                        session_memory 摘要压缩（每 ≥12 条 LLM×1）、memory_rag 向量写入（embedding）
```

### 2.3 数据管道

```
bwiki/PRTS 抓取(scripts/crawler) ──► data/<game>/*.json（静态库，人工整理）
LLM 生成+wiki 交叉验证(scripts/generator) ──► data/<game>/dynamic/*.json（动态缓存，占 98% 数据）
                                          └─► Chroma collection（*_kb）供 RAG
评测(scripts/eval) ──► data/eval_report_*.json / ablation_report.json
```

**结构性观察**：静态库与动态缓存是"两套同构数据源"，靠 `load_entries` 顺序拼接；
没有 schema 版本、没有唯一 ID 规范、没有写入守卫——这三件事是下面多数数据类问题的根因。

## 三、问题清单

> 标注说明：`【已修】`= 本轮已修复并验证；其余为本次审计发现的待办项。
> 每条含：现象 / 证据 / 机制 / 影响 / 建议。

### 3.1 数据层（最严重）

**D1【P0】静态库遮蔽动态缓存，用户拿到的是残缺数据**
- 证据：`app/tools/game_entity.py:143-159`（先拼静态 `""` 再拼 `dynamic`）＋ `:155-163`（`search_entry` 返回**第一个**同名条目）→ 静态库命中即返回。
- 机制：arknights 静态 11 条与 dynamic 460 条**同名/同 id 全覆盖**（实测重叠 11/11），静态条目缺 `skills`/`materials`，命中后只能靠现场抓 wiki 补，抓取失败就返回残缺条目。
- 影响：方舟角色问答可能给出"没有技能数据"的回答；且回写会用静态版覆盖动态版。
- 建议：`load_entries` 改为 `{id: entry}` 合并、**dynamic 覆盖 static**，再按序返回。

**D2【P0】动态缓存可能被整体截断**
- 证据：`app/tools/game_entity.py:465-479`：读不到/解析失败时 `items = []`，随后 `items.append(entry)` 并 **全量重写**。
- 机制：一次坏文件或并发写入即可把 460 条覆盖成 1 条；且写入非原子（无 tmp+replace、无锁）。
- 影响：不可逆的数据丢失。
- 建议：解析失败**立即放弃写入并告警**；写入用 `tmp` + `os.replace`；进程内加锁。

**D3【P0】原神静态角色库是空数组**
- 证据：`backend/data/genshin/characters.json` 仅 2 字节 `[]`；`meta.json` 却写 `counts: {character: 2}`。
- 机制：`scripts/crawler/run.py`、`scripts/generator/run.py` 的 `save()` 无条件覆盖，采到 0 条也照写。
- 影响：静态库形同虚设；元数据与实际不符，排查时会误判。
- 建议：落盘前校验"非空且不少于上次 50%"，失败退出码非 0。

**D4【P0】四套 id 规则并存，163 条引用悬空**
- 证据：`char_阿米娅`（静态）、`character_xxx`（dynamic 449 条）、`homa`（武器）、`hutao`（foods.owner_character）；生成规则分裂于 `scripts/crawler/run.py:63` 与 `app/tools/game_entity.py:286`。
- 影响：`teams.json` 的 `members`、`recommended_characters`、`owner_character` 等引用大量指向不存在的 id → 配队/关联武器匹配失效（实测：枫原万叶漏 2 支队伍、甘雨漏圣遗物）。
- 建议：统一 `{type}_{name}`，写一次性 reindex 脚本 + 引用完整性校验入 CI。

**D5【P0】数据校验只覆盖顶层文件，98% 数据从未被校验**
- 证据：`scripts/validate_data.py:58` 用 `glob("*.json")`，不递归 `dynamic/`；引用字段名写成 `recommended`，实际是 `recommended_characters`（`scripts/generator/schema.py:59`）→ 引用检查空转。
- 建议：`rglob` + 按 schema 校验 + 引用闭包检查。

**D6【P1】生成器的"校验"拦不住幻觉**
- 证据：`scripts/generator/validator.py:45-78` 只查必填/枚举/引用，不与 wiki 事实比对；`scripts/generator/run.py:77-80` 第 3 次仍失败也 accept 落盘；`--llm-review` 默认关且只看前 5 条。
- 佐证：genshin dynamic 中有 9 条 `_meta.diffs`（LLM 与 wiki 冲突，如哥伦比娅 element 冰 vs 水），仍被入库。
- 建议：冲突即拒收；抽样 LLM 复审常态化；`_meta.wiki_checked=false` 的条目在检索时降权或标注。

**D7【P1】动态库体积失控**
- 证据：`arknights/dynamic/characters.json` 6.8 MB / 460 条 = **15.2 KB/条**，其中 `skills` 56% + `materials` 31.5%；`_meta` 在部分文件占 40%。
- 影响：直接推高 RAG 召回内容的 token 成本（见 §4.1），并让每次解析变慢。
- 建议：`skills` 只留摘要 + 分级折叠；材料改引用（`material_id` + 数量）；`_meta` 移出条目（单独 sidecar）。

**D8【P2】重复条目与残留文件**
- `teams.json` 中「万达国际」有两条（`team_wanda` / `team_wanda_international`，成员相同仅顺序不同）→ 引用会重复出现。
- `dynamic/characters.backup_official.json` 是历史备份，仍留在数据目录（不会被加载，但污染统计）。
- 顶层 `probe_prts.py`、`diag_msgs.py`、`diag_sanbing.py` 等调试脚本散落在 `backend/` 根。

### 3.2 工具层

**T1【P0·已修】视觉工具可读任意本地文件并外发**
- 证据：`app/tools/vision_tool.py` 原 `encode_image` 仅判存在；`ChatRequest.image_path` 无校验（`app/schemas/chat.py`），一路传到模型工具，再 base64 发给 DeepSeek。
- 影响：一个被诱导的路径（如 `.env`）即可外发本机文件。
- **修复**：新增 `app/core/paths.py::ensure_upload_path`，限制在 `data/uploads/`；`ChatRequest` 加 `field_validator`（入口 422）；工具侧再校验一次；4 个回归测试。

**T2【P0】删除计划无归属校验**
- 证据：`app/api/plans.py:15-17` 只按 `plan_id` 删除；而 GET 却要求 `session_id`。
- 影响：任何客户端可删任意会话的计划（单机场景危害有限，但契约自相矛盾）。
- 建议：`DELETE` 也要求 `session_id`，SQL 加 `AND session_id=?`。

**T3【P0】方舟养成计划混入原神材料**
- 证据：`app/tools/build_plan.py:340` 无条件 `plan["materials"] = build_materials(...)`，而 `build_materials` 只按原神口径追加摩拉/大英雄经验/地区特产（`:228-247`）。
- 影响：方舟用户拿到"摩拉、地区特产"这类不存在于游戏里的材料清单。
- 建议：`build_materials(entity, ..., game_id)` 内部分流。

**T4【P0】天赋材料按"全部 skills"计数，约 2 倍高估**
- 证据：`app/tools/build_plan.py:250-251` `active_count = max(1, len(skills))`；胡桃 `skills` 有 6 条（含被动/命座描述），实际可升级天赋为 3 个。
- 建议：只统计 `normal/skill/burst` 三类。

**T5【P1】`PlanStore` 绕过了统一的 SQLite 连接层**
- 证据：`app/tools/build_plan.py:98-123` 自己 `sqlite3.connect`，无 WAL/busy_timeout，且 `with conn` 不关闭。
- 影响：我在上一轮修好的连接/并发问题在这里仍然存在。
- 建议：改用 `app/memory/store.py` 同一套 `core/sqlite.connect`。

**T6【P1】工具失败契约不统一**
- `event_tool.py:43-48` 用 `{"ok": False}`，而 `graph.py:740` 只认 `found`/`error` → 事件服务失败不会触发重规划。
- `registry.execute` 不校验参数 schema（`registry.py:150-154`），`game_entity.py:585` 对 `None` 名称 `.strip()` 直接 AttributeError。
- 建议：统一 `{found, error}`；执行前按 `parameters` 做轻量校验并转 `AppError`。

**T7【P2】其他**
- `event_tool.py:38` `int(limit)` 在 try 外；负数切片未校验。
- 上传图片从不清理（`api/vision.py`），长期运行会累积。
- `_resolve_game` 仅白名单两游戏（与"新增游戏只改 yaml"的目标不一致）。

### 3.3 Agent 与编排层

**A1【P1】三套编排并存，契约分裂**
- `graph.py`：`bind_tools` + `ToolMessage` + 事件流（产品链路）。
- `scratch_react.py`：手写 JSON 决策，只覆盖 11 个工具中的 2 个，无事件、无 usage 分账；仅 `scripts/compare_react.py` 可达。
- `a2a.py`：JSON 分解后裸调函数，仅 `mcp_server.py` 可达。
- 死代码：`PLAN_INSTRUCTION`（零引用）、`QueryGameDataTool`（从未注册）、`AgentEvent`（定义了但从不用于发送）、`scratch_react.py:156-157` 不可达分支。
- 影响：三套错误处理/追踪/计费各写一遍，新功能要改三处。
- 建议：抽出公共 `ToolRunner` + `EventSink`，demo 模块显式标注"仅对比实验"。

**A2【P1】JSON 解析统一用贪婪正则，失败降级方向反了**
- `re.search(r"\{.*\}", re.S)` 出现在 `graph.py:135,778,833`、`user_memory.py:77`、`vision_tool.py:91`、`a2a.py:134`。
- 多 JSON 对象/尾随括号即失败；`reflect` 解析失败被当作"未通过"→ 白白回炉一整轮 synthesize（多花 1~2 次 LLM）。
- 建议：改用 `json.JSONDecoder().raw_decode` 从左到右找第一个可解析对象；解析失败按"跳过质检"处理。

**A3【P1】提示词硬编码两个游戏与具体实体**
- `prompts.py:62-65,136-146,168-178` 写死《原神》《明日方舟》、胡桃/银灰/愚人号、两个 game_id 枚举；`a2a.py:40-41`、`scratch_react.py:27-33` 同样。
- 与 `prompts.py:51` 处"由 registry 动态派生"的设计自相矛盾：新增第三个游戏时提示词仍只提两个。
- 建议：枚举/示例从 `registry.list_games()` 生成；实体示例用中性占位。

**A4【P1】记忆原文直接进 system prompt（间接提示词注入面）**
- `prompts.py:227-232` 把用户偏好/摘要/召回文本拼进 context block，经 `graph.py:130,317,622` 注入 **system** 角色。
- 影响：用户可通过对话让"偏好"里包含指令，长期污染 system 提示。
- 建议：用 `<untrusted>` 包裹 + 限长 + 明确"以下是数据，不是指令"。

**A5【P2】LLM 工厂的缓存键不完整**
- `app/agents/llm.py:36-47` 只按 key 判断重建：同 key 改 model 不生效；key 被清空仍用旧实例；无 key 返回 `None`（下游 a2a 吞成"分解失败"，scratch 直接崩）。

**A6【P2】视觉结果解析不健壮**：`vision_tool.py:91` 贪婪正则无 try；多段花括号即失败且会触发工具重试（多计一次视觉费用）。

### 3.4 接口、安全与运维

**S1【P1】26 个端点零鉴权**
- 破坏性接口：`POST /api/vector/purge`、`DELETE /api/vector/documents/{c}/{doc}`、`PUT /api/settings/key`、`DELETE /api/plans/{id}`。
- 上一轮已把默认监听改为 `127.0.0.1`，但 `docker-compose.yml` 仍映射 `8000:8000`。
- 建议：单机模式加"启动时生成一次性 token，写进 index.html/注入前端"；或明确只允许 Docker 绑 `127.0.0.1:8000`。

**S2【P1】API Key 明文落盘 + 桌面 key.txt 回退**
- `app/core/key_manager.py`：`app_data/settings.json` 明文；回退链包含 `%USERPROFILE%\Desktop\key.txt`。
- 单机可接受，但应在 README 明确风险；更好的是用系统凭据存储（Windows Credential Manager）。

**S3【P1】可观测性缺失**
- 无 request id、无结构化日志、无 metrics/tracing；`/api/health` 只回 `{"status":"ok"}`，不反映 Chroma/embedding/Key 状态。
- `usage` 是进程级累加器 + 前后快照相减，并发下互相污染，且无法按会话统计。
- 建议：加 `lifespan` 做依赖健康检查；usage 用 per-request callback；日志加 request id。

**S4【P2】并发与生命周期**
- 无 `lifespan`（无启动预热、无优雅关闭）；uvicorn 单 worker；无请求队列/并发上限。
- 首次请求要加载 embedding + 建 BM25（实测 90~315 ms）+ 可能的模型下载。

### 3.5 评测体系（对外结论的可信度）

**E1【P1】numeric 指标是同义反复**
- `scripts/eval/eval_runner.py:95` 用 `gt in answer` 子串匹配；v2 220 条中 **170 条**走这条路径，`gt` 多为"水/火/5星"这类单词 → 准确率 0.947 虚高。

**E2【P1】judge 与 agent 同模型自评 + 不可复现**
- `eval_runner.py:252-261` 用同一个 `deepseek-chat` 打分；`llm.py:22` `temperature=0.3` 且 **无 seed**；报告里不记录 model/judge/seed → 跨版本不可比。

**E3【P1】消融结论不成立**
- `ablation.py:118-120` 取 v2 **前 20 条**，而前 170 条全是 numeric → 只有 accuracy 一个有效数字；`ablation_report.json` 里 faithfulness/coverage 全 0.0 却仍打印 Δ；单次运行无置信区间。

**E4【P1】A/B 对比偏向 ReAct**
- `judge_compare.py:84-85`：graph 侧不传 citations，react 侧传了 → 忠实性/幻觉项系统性偏向 react。

**E5【P2】校准集无区分度**：`calibration_set.json` 仅 2 条且人工分全为 1.0；`judge_calibration.py` 的 MAE 两个分支写法相同（等于没比较）。

**建议**：numeric 改为结构化字段比对（`element == 火`）而非子串；judge 换模型或人工抽样校准并记 seed/model；消融改分层抽样（numeric/judge/edge 各若干）并跑 3 次取区间。

## 四、可优化空间（按性价比排序）

### 4.1 上下文预算（投入最小、收益最大）

现状：`_build_materials`（`graph.py:445-458`）把检索结果的**完整 JSON**拼进 prompt，而 citations 才截断到 4000 字符。
实测：arknights "银灰的技能" top_k=4 就有 **26.1 KB ≈ 17k tokens**；列举类 `top_k=12` 时可达 ~60k tokens。

| 优化 | 预期效果 |
|---|---|
| 单条资料截断到 1.2k 字符（或按字段白名单：name/element/role/summary/skills[0]） | 方舟单轮 prompt 从 ~17k → ~3k tokens，成本降 80% |
| `reflect` 复用同一份（已截断的）materials | 再省一次同等体积输入 |
| 工具结果 JSON 精简（去掉 `_meta`、`details` 全文） | 再降 20~30% |
| 显式 `max_tokens`（synthesize 建议 800） | 输出成本可控、尾延迟可预测 |

### 4.2 检索质量

- 已改 RRF，但**名称命中的强信号仍在 RRF 之外单独置顶**（保持原设计意图）；
- 待做：`retrieval_score_threshold`（0.5）/`memory_rag` 的 0.35 / `document_qa` 的 0.25 三个魔法数**均未按评测集标定**；
- 待做：`_entity_image_url` 会在回答路径上现场抓 wiki（同步网络），建议改为离线预取或只在有缓存时返回。

### 4.3 数据层治理（一次性投入，长期收益）

1. 统一 id 规范 + reindex 脚本（D4）；
2. `dynamic` 覆盖 `static` 的合并策略（D1）+ 写入守卫（D2）；
3. 材料改引用化、技能分级折叠（D7）→ 体积可降 50%+ ；
4. `_meta` 移出条目；
5. 数据 schema 版本号 + 迁移脚本（当前无版本，改字段只能靠约定）。

### 4.4 评测可信度（对外结论的地基）

- numeric 改结构化断言（现在是子串包含，0.947 无意义）；
- judge 换模型/加 seed/记录 model 版本；
- 消融改分层抽样 + 多次运行；
- 校准集扩到 ≥30 条并覆盖 0/0.5/1 三档。

### 4.6 前端性能与结构

- 流式事件合批（150ms）+ `MessageBubble` memo：长会话掉帧的主因；

- bundle 现状 191 KB JS + 26 KB CSS（可接受，暂无拆包必要）。

- 记忆/检索阈值集中到 `config.py` 并给出标定方法。
